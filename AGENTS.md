# SOS Amende — LegalTech SaaS (contestation d'amendes FR)

French LegalTech SaaS: the client pays upfront (reversed onboarding), uploads their PV, OCR/IA extracts data, a pre-seeded legal-failure DB matches a loophole, a dynamic letter is generated, the client signs electronically, a jurist validates, and the contestation is submitted automatically to the ANTAI mock portal (dev/E2E) — in prod the submission fails and the client sends it by LRAR (Option A v1 fallback). Repo is at **v1 scope**: Flux Amende complet (paiement d'abord → upload → OCR human-in-the-loop → faille → lettre + signature → validation juriste → envoi auto ANTAI / kit LRAR → décision OMP), stockage local/S3, migrations Prisma. Full product vision lives in `PLAN.md`; this file is operational guidance for the actual codebase.

## Architecture (App Router)

- Route groups: `(marketing)` (landing, `/pricing`, legal pages), `(auth)` (`/login`, magic-link verification), `(app)/dashboard` (protected). Path alias `@/*` → `./src/*`. La landing est `(marketing)/page.tsx` (le `src/app/page.tsx` par défaut create-next-app a été supprimé — ne pas le recréer, il écrase le route group). **Analyse démo (landing)** : `src/components/demo-scan.tsx` (aucun upload ni saisie — la démo simule le téléversement d'un échantillon d'avis de contravention ou de décision de suspension + type AMENDE/SUSPENSION → POST `src/app/api/demo/analyse/route.ts`) — OCR mock en dev + `detecterFailles` sur les failles **ACTIVE** (validées) **et PROPOSEE** (propositions du catalogue étiquetées « Proposition à valider » dans l'UI, jamais INACTIVE) + `scoreFaille` (score par règles matchées) ; **score global de réussite** (`scoreGlobal` = meilleur score parmi les failles détectées) ; **lettre démo générée** (`remplirTemplate` depuis le template de la faille principale, identité fictive « Alex Martin ») ; étapes animées scan → score → lettre ; libellés type-aware (avis de contravention vs décision de suspension) ; bandeau « Simulation de démonstration », **aucune donnée stockée** (RGPD), résultat jamais présenté comme un avis juridique.
- Auth: next-auth v5 beta + `@auth/prisma-adapter` + Resend magic link (no passwords) in `src/auth.ts`. JWT session strategy (`auth.config.ts`) with role injected via callback; middleware in `src/proxy.ts` guards `/dashboard`.
- Use `src/lib/dal.ts` (`getCurrentUser`, `requireUser`, `requireJuriste`, `requireAdmin`) for server-side auth/data access — it is `server-only`. Don't call `auth()` ad hoc in server components/actions. `requireJuriste` autorise `JURISTE` ou `ADMIN`.
- Server actions live in per-feature `actions.ts` files (`"use server"`), e.g. `(auth)/login/actions.ts`, `(app)/dashboard/actions.ts`, `(app)/dashboard/cases/actions.ts` (`createDossier` : crédit requis, fichier stocké via `storageWrite` — `public/uploads/` en local, S3 en prod —, `Dossier` créé en `EN_ANALYSE`, crédit décrémenté). `next.config.ts` a `experimental.serverActions.bodySizeLimit = "10mb"` pour l'upload du PV.
- Env vars referenced in code: `DATABASE_URL`, `AUTH_RESEND_KEY`, `EMAIL_FROM` (expéditeur Resend — domaine vérifié en prod, jamais `onboarding@resend.dev` sandbox ; requis sinon Resend refuse l'envoi), `NEXT_PUBLIC_APP_URL`, `ANTAI_MOCK_TOKEN` (token du mock ; **sans valeur par défaut en prod** — le mock `/api/antai/mock` refuse la production sauf opt-in `ANTAI_MOCK=1` réservé aux E2E, config `playwright.config.ts` webServer.env), `OCR_PROVIDER` (`mock`|`google-vision`|`mistral-ocr`|`tesseract`) + `GOOGLE_VISION_KEY` / `MISTRAL_API_KEY` (alternatives : Mistral OCR = API hébergée UE/RGPD ; Tesseract.js = local gratuit, aucune donnée ne quitte la machine), `STORAGE_DRIVER` (`local`|`s3`) + `STORAGE_BUCKET`/`STORAGE_REGION`/`STORAGE_ENDPOINT`/`STORAGE_ACCESS_KEY`/`STORAGE_SECRET_KEY` (S3-compatible UE), `TRAVAUX_OPENDATA_BASE` (base OpendataSoft des travaux routiers pour les **preuves externes** — défaut : Sarthe), `CRON_SECRET` (**requis hors dev** pour `/api/cron/rappels` **et** `/api/cron/auto-alimentation` — sinon 500 en prod), `AUTH_DEV_FILE` (`1` = autorise le fallback fichier magic-link même en build prod, uniquement E2E), `SUPER_ADMIN_EMAIL` (email du super admin : à sa première connexion magic-link, `events.signIn` dans `src/auth.ts` l'élève en `ADMIN` côté serveur — permet de provisionner le premier admin sans accès base, cf. `scripts/creer-compte.ts`), (plus standard next-auth `AUTH_SECRET`/`AUTH_URL`). `.env` is gitignored ; la référence est `.env.example`. **Stripe n'existe plus en V1** : aucun code, route, paquet ou clé `STRIPE_*` dans le repo (champs `stripeCustomerId`/`stripePaymentId` conservés inertes dans le schéma pour un retour futur).
- Paiement (inscription inversée, section 3) : **virement bancaire = seul mode de paiement V1** (Stripe retiré). Page publique `/paiement` (`src/app/(marketing)/paiement/`) et espace client `paiement/[id]` : `payerParVirement` (`paiement/actions.ts`) crée un `Payment` `PENDING_VIREMENT`, RIB affiché, « J'ai effectué le virement » → upload de la preuve (JPEG/PNG/WebP/PDF ≤ 8 Mo, `api/paiement/virement/preuve` + `src/components/preuve-virement-upload.tsx`, `storageWrite`) → admin (`admin/paiements`) valide/refuse via `validerVirement` (`admin/paiements/actions.ts` : `PAID` + `credits +1` + `notifierPaiementValide` ; `PENDING_VIREMENT` seul paiement accepté). **Paywall crédits épuisés** : quand `credits < 1`, le dashboard, `cases/` et `cases/new` affichent un bandeau de paiement avec `src/components/payer-cta.tsx` (bouton → `/paiement?type=AMENDE|SUSPENSION`) au lieu d'un formulaire de dépôt. **Le paiement ne concerne que le client** : `/dashboard` redirige le JURISTE vers `/dashboard/juriste` et l'ADMIN vers `/dashboard/admin/dossiers` (suivi des dossiers) ; `PayerCta` et « Nouveau dossier » sont masqués pour les non-CLIENT, `/dashboard/cases/new` redirige les non-CLIENT, « Mes dossiers » n'apparaît qu'en nav client. ## Data model — schema actuel (aligné sur la section 4 du cahier des charges)

`prisma/schema.prisma` suit les noms de la section 4 du cahier des charges (décision validée : remplacement des anciens modèles `Case`/`Ticket`/`LegalRule`/…). Modèles métier :
- `User` (rôle enum `CLIENT` | `JURISTE` | `ADMIN`, défaut `CLIENT`), champs spec `passwordHash`, `stripeCustomerId` (inerte), `credits` — en plus des champs obligatoires next-auth (`emailVerified`, `name`, `image`).
- `Preuve` (`dossierId`, `userId`, `url` (stockage), `nom`, `type`, `createdAt`, `@@index([dossierId])`, cascade) — pièces jointes versées au dossier par le **client ET le juriste** (RGPD/contestation). Actions partagées dans `src/app/(app)/dashboard/preuves/actions.ts` (`ajouterPreuve`, `supprimerPreuve` : accès client propriétaire OU juriste ; storageWrite, événement `PREUVE`) ; composant `src/components/preuves.tsx` ; intégré au détail client `cases/[id]` **et** juriste `juriste/[id]` ; inclus dans l'export RGPD et supprimé (fichiers) lors de l'effacement du compte. **Preuves externes auto-récupérées** : `src/lib/preuves-api.ts` (`geocoderAdresse` BAN, `preuveMeteo` Open-Meteo archive, `rechercherRadar` radars.csv data.gouv.fr mise en cache, `rechercherTravaux` OpendataSoft) — `recupererPreuvesPourDossierId` crée les `Preuve` de types `METEO`/`RADAR`/`TRAVAUX` (`url` vide + {badge « Récupérée »), écrit `conditions_meteo` sur `Dossier` et reçoit lat/lon dans `extractedData` ; appelé à l'**analyse automatiquement** (best-effort) et à la demande via `recupererPreuvesApi` (bloc `PreuvesApiBlock` sur `juriste/[id]`). **La lettre mentionne les preuves récupérées et les met en pièces jointes** : `listePiecesJointes` (pure, testée) construit l'inventaire procédural (copie du PV/décision + chaque preuve réellement en base, conditions météo rappelées) ; `generateLettrePdf(texte, signature, piecesJointes)` rend la section « Pièces jointes » avant la signature — appliquée à toutes les générations (`signerDossier`, `validerDossier` Cas A, `modifierLettre`, route `/api/dossier/[id]/lettre`) et l'accusé mock reçoit les mêmes libellés (jamais de preuve non récupérée, garde-fou anti-hallucination). **Le corps de la lettre cite aussi les pièces par écrit** : `paragraphePiecesVersees` + `lettreAvecPiecesVersees` (pures, testées) ajoutent un paragraphe factuel « Pièces versées à l'appui de la contestation » à la fin de `lettreGeneree` — appliqué à l'analyse (`analyserDossier`), à la vérification poussée, à `validerDossier` (rattrape aussi les lettres analysées avant cette évolution) et à `confirmerFaille`.
- `Dossier` (type `AMENDE`|`SUSPENSION`; statut `BROUILLON→EN_ANALYSE→A_VERIFIER→PRET→ENVOYE→REJETE→ERREUR_TECHNIQUE→RESOLU→ANNULE`), `pvUrl`, `pvTexte` (texte brut OCR, pour la détection par scan), `extractedData` (JSON OCR), `lettreGeneree`, `motifRejet` (raison du rejet juriste), `decisionOmp` (`ACCEPTE`|`REJETE`) + `decisionDetail` (décision OMP post-envoi), `valideLe` (validation de la lettre par le juriste → kit LRAR), `dateLimite` (délai de contestation calculé par le moteur), `prix`, `failleJuridiqueId` (faille principale retenue), `faillesRetenues` (`DossierFaille[]`). Timeline de transparence : chaque transition écrit un `DossierEvent` (`type` enum CREATION/ANALYSE/LETTRE_GENEREE/EN_ATTENTE/SIGNATURE/VALIDATION/ENVOI/DECISION/REJET/RETOUR/**PREUVE**, `detail` = accusé, motif ou décision) dans le même `$transaction` que le changement de statut ; affichée sur les détails client **et** juriste via `src/components/dossier-timeline.tsx`.
- Moteur juridique : `src/lib/moteur.ts` (pur, sans `server-only`) — `remplirTemplate` (variables `{nom}`, `{plaque}`, `{num_pv}`…), `detecterFailles(data, texte, failles, contexte)` : **base juridique auto-alimentée** — une faille est candidate si **l'une au moins** de ses règles (`FailleJuridique.reglesDetection`, types `champAbsent`/`datePrescrite`/`plaqueIncorrecte`/`etalonnageExpire`/`texteContient`/`texteAbsent`) matche sur les données extraites **et/ou le texte brut scanné** (`Dossier.pvTexte`) ; sans règles explicites, prédicats hérités pour les 4 failles connues ; retour dans l'ordre de priorité (prescription > erreur plaque > mentions > étalonnage), `detecterFaille` = premier candidat (retourne `null` sans indice — plus de « fallback étalonnage » fabriqué). `datePrescrite`, `dateLimitePv` (45 j amende / 2 mois suspension), `joursRestants`, `etalonnageExpire(dateExpiration, datePv)`, `scoreFaille` (score de confiance démo : règles matchées / règles totales, `null` si non candidate ; sans règles, prédicat hérité 1/1). Tests unitaires Vitest dans `src/lib/moteur.test.ts`. `analyserDossier` (`cases/actions.ts`) remplit `extractedData` (saisie humaine, human-in-the-loop), calcule le contexte étalonnage (radar → date d'expiration), enregistre **toutes les failles candidates** dans `DossierFaille` (statut CANDIDATE, après réinitialisation), retient la première comme `failleJuridiqueId`, génère `lettreGeneree` depuis `templateLettre`, calcule `dateLimite` et passe le statut en `A_VERIFIER`. **Questionnaire ciblé (flux A) :** `extractedData` contient aussi `paiementDejaFait`, `vehiculeCede`, `vehiculeVole`, `conducteurDifferent` (checkboxes du formulaire d'analyse, pré-remplis par OCR jamais) — contexte transmis au juriste (affiché sur son détail, aucun article inventé) ; les lettres restent limitées aux `FailleJuridique` validées admin. Si `radarId` est saisi et qu'un `RadarCalibration` existe avec un certificat expiré le jour de l'infraction (`etalonnageExpire`), la faille « certificat d'étalonnage » est retenue et `preuveEtalonnage` (URL du certificat) est stockée dans `extractedData` et affichée sur le détail.
- OCR (Phase 1, garde-fou human-in-the-loop) : `src/lib/ocr.ts` — providers via `OCR_PROVIDER` (`mock` = dev/E2E, `google-vision` = Google Vision API si `GOOGLE_VISION_KEY` set, `mistral-ocr` = Mistral AI hébergement UE/RGPD si `MISTRAL_API_KEY` set, `tesseract` = Tesseract.js local/gratuit, sinon `aucun`), `normaliserPv(texte)` (pur, regex : plaque SIV/FNI, date, heure, montant, n° PV — tests Vitest dans `src/lib/ocr.test.ts`). `createDossier` lance `extrairePv` sur le PV et **pré-remplit** `extractedData` (statut reste `EN_ANALYSE`) ; le formulaire d'analyse (`analyse-form.tsx`, `defaultValue` depuis `prefill`) affiche « pré-remplis par lecture automatique (OCR) » et l'humain vérifie avant soumission. L'OCR n'écrit jamais l'analyse finale seul.
- `FailleJuridique` = base des failles juridiques (typeInfraction, titreFaille, `articleLoi`, `regle` — règle dégagée : ce que l'article + la jurisprudence imposent, `templateLettre` avec variables `{nom}`, `{plaque}`, `{num_pv}`, `{date}`, `{montant}`, `{radarId}`, `source`, `reglesDetection` JSON, `jurisprudence` JSONB (tableau `JurisprudenceRef` avec `resume` — l'essentiel de chaque décision, contextualisé), statut `ACTIVE`/`INACTIVE`/`PROPOSEE`) ; `DossierFaille` (dossierId+failleId unique, statut `CANDIDATE`|`CONFIRMEE`|`REJETEE`) relie chaque dossier à toutes ses failles détectées — les validations du juriste alimentent la base. **Flux SUSPENSION (infra, sans contenu juridique inventé)** : `src/lib/envoi.ts` (pur, testé) fournit les libellés type-aware (destinataire LRAR préfet vs OMP, délais 2 mois vs 45 j, labels du formulaire) ; le formulaire d'analyse (`analyse-form.tsx`) adapte ses labels et masque le questionnaire amende pour SUSPENSION ; callout d'urgence générique « délais de recours très courts » sur les détails client **et** juriste ; l'admin (`juriste/failles`) affiche un rappel tant qu'aucun template SUSPENSION `ACTIVE` n'existe. Le catalogue (`catalogue-sources.ts`) porte désormais **3 propositions SUSPENSION** (`verifiee: false` — CE 20 avr. 2021 n° 438114 contradictoire préalable ; CE 14 févr. 2018 n° 407914 marge d'erreur éthylomètre 8 % ; non-notification L. 224-16/R. 224-4 CR) qui arrivent en `PROPOSEE` par l'auto-alimentation — le moteur ne les utilise qu'après validation admin (`ACTIVE`), garde-fou anti-hallucination.

## Product guardrails (spec constraints — apply to all work)

- **Never invent or hallucinate a legal article.** Letters may only use admin-validated `FailleJuridique.templateLettre` templates.
- OCR output is never sent directly — a human verification step is mandatory (human-in-the-loop).
- Reversed onboarding: client pays first (virement bancaire V1), the admin credits the account after validation of the transfer proof, then the case is created. Payment-first, not signup-first.
- ANTAI submission must be tested against a local mock page, never the real portal (dev/E2E).
- Infraction data is sensitive: RGPD, EU hosting, no secrets in code or commits.
