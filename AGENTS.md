# SOS Amende — LegalTech SaaS (contestation d'amendes FR)

French LegalTech SaaS: the client pays upfront (reversed onboarding), uploads their PV, OCR/IA extracts data, a pre-seeded legal-failure DB matches a loophole, a dynamic letter is generated, the client signs electronically, a jurist validates, and the client sends it by LRAR (Option A v1). Repo is at **v1 scope**: Flux Amende complet (paiement d'abord → upload → OCR human-in-the-loop → faille → lettre + signature → validation juriste → kit LRAR → décision OMP), stockage local/S3, migrations Prisma. Full product vision lives in `PLAN.md`; this file is operational guidance for the actual codebase.

## Architecture (App Router)

- Route groups: `(marketing)` (landing, `/pricing`, legal pages), `(auth)` (`/login`, magic-link verification), `(app)/dashboard` (protected). Path alias `@/*` → `./src/*`. La landing est `(marketing)/page.tsx` (le `src/app/page.tsx` par défaut create-next-app a été supprimé — ne pas le recréer, il écrase le route group). **Analyse démo (landing)** : `src/components/demo-scan.tsx` (aucun upload ni saisie — la démo simule le téléversement d'un échantillon d'avis de contravention ou de décision de suspension + type AMENDE/SUSPENSION → POST `src/app/api/demo/analyse/route.ts`) — OCR mock en dev + `detecterFailles` sur les failles **ACTIVE** (validées) **et PROPOSEE** (propositions du catalogue étiquetées « Proposition à valider » dans l'UI, jamais INACTIVE) + `scoreFaille` (score par règles matchées) ; **score global de réussite** (`scoreGlobal` = meilleur score parmi les failles détectées) ; **lettre démo générée** (`remplirTemplate` depuis le template de la faille principale, identité fictive « Alex Martin ») ; étapes animées scan → score → lettre ; libellés type-aware (avis de contravention vs décision de suspension) ; bandeau « Simulation de démonstration », **aucune donnée stockée** (RGPD), résultat jamais présenté comme un avis juridique.
- Auth: next-auth v5 beta + `@auth/prisma-adapter` + Resend magic link (no passwords) in `src/auth.ts`. JWT session strategy (`auth.config.ts`) with role injected via callback; middleware in `src/proxy.ts` guards `/dashboard`.
- Use `src/lib/dal.ts` (`getCurrentUser`, `requireUser`, `requireJuriste`, `requireAdmin`) for server-side auth/data access — it is `server-only`. Don't call `auth()` ad hoc in server components/actions. `requireJuriste` autorise `JURISTE` ou `ADMIN`.
- Server actions live in per-feature `actions.ts` files (`"use server"`), e.g. `(auth)/login/actions.ts`, `(app)/dashboard/actions.ts`, `(app)/dashboard/cases/actions.ts` (`createDossier` : crédit requis, fichier stocké via `storageWrite` — `public/uploads/` en local, S3 en prod —, `Dossier` créé en `EN_ANALYSE`, crédit décrémenté). `next.config.ts` a `experimental.serverActions.bodySizeLimit = "10mb"` pour l'upload du PV.
- Env vars referenced in code: `DATABASE_URL`, `AUTH_RESEND_KEY`, `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_PRICE_MONTHLY`, `STRIPE_PRICE_AMENDE`, `STRIPE_PRICE_SUSPENSION`, `STRIPE_MOCK` (`1` = portail de paiement local `/mock-stripe`, jamais actif en prod), `NEXT_PUBLIC_APP_URL`, `ANTAI_MOCK_TOKEN` (défaut `dev-antai-mock` ; uniquement mock local, jamais le portail réel), `OCR_PROVIDER` (`mock`|`google-vision`|`mistral-ocr`|`tesseract`) + `GOOGLE_VISION_KEY` / `MISTRAL_API_KEY` (alternatives : Mistral OCR = API hébergée UE/RGPD ; Tesseract.js = local gratuit, aucune donnée ne quitte la machine), `STORAGE_DRIVER` (`local`|`s3`) + `STORAGE_BUCKET`/`STORAGE_REGION`/`STORAGE_ENDPOINT`/`STORAGE_ACCESS_KEY`/`STORAGE_SECRET_KEY` (S3-compatible UE), `CRON_SECRET` (optionnel, protège `/api/cron/rappels` **et** `/api/cron/auto-alimentation`) (plus standard next-auth `AUTH_SECRET`/`AUTH_URL`). `.env` is gitignored ; la référence est `.env.example`.
- Stripe (inscription inversée, section 3) : `/api/stripe/checkout` (POST `{type: AMENDE|SUSPENSION}` → session 39€/59€ via `price_data`, fallback price IDs) et `/api/stripe/webhook` (`checkout.session.completed` → crée le user par email si absent, `credits +1`, `stripeCustomerId`, enregistre `Payment`). Logique de crédit partagée dans `src/lib/paiement.ts::traiterPaiement` (webhook réel **et** mock). Sans `STRIPE_SECRET_KEY`, checkout renvoie 400 ; le webhook requiert `STRIPE_WEBHOOK_SECRET`. **Paywall crédits épuisés** : quand `credits < 1`, le dashboard, `cases/` et `cases/new` affichent un bandeau de paiement avec `src/components/payer-cta.tsx` (POST `/api/stripe/checkout` → redirection session) au lieu d'un formulaire de dépôt. **Le paiement ne concerne que le client** : `/dashboard` redirige le JURISTE vers `/dashboard/juriste` et l'ADMIN vers `/dashboard/admin/failles` ; `PayerCta` et « Nouveau dossier » sont masqués pour les non-CLIENT, `/dashboard/cases/new` redirige les non-CLIENT, « Mes dossiers » n'apparaît qu'en nav client. **Mock local** (dev/E2E, garde-fou) : `STRIPE_MOCK=1` → checkout renvoie l'URL du portail `/mock-stripe`, qui appelle `/api/stripe/mock/complete` (simule `checkout.session.completed`) ; testé par `e2e/paiement.spec.ts` (payer → compte crédité → connexion magic-link → dashboard).
- UI: Tailwind v4 (`@tailwindcss/postcss`), shadcn-style components in `src/components`, French UI copy throughout.

## Data model — schema actuel (aligné sur la section 4 du cahier des charges)

`prisma/schema.prisma` suit les noms de la section 4 du cahier des charges (décision validée : remplacement des anciens modèles `Case`/`Ticket`/`LegalRule`/…). Modèles métier :
- `User` (rôle enum `CLIENT` | `JURISTE` | `ADMIN`, défaut `CLIENT`), champs spec `passwordHash`, `stripeCustomerId`, `credits` — en plus des champs obligatoires next-auth (`emailVerified`, `name`, `image`).
- `Preuve` (`dossierId`, `userId`, `url` (stockage), `nom`, `type`, `createdAt`, `@@index([dossierId])`, cascade) — pièces jointes versées au dossier par le **client ET le juriste** (RGPD/contestation). Actions partagées dans `src/app/(app)/dashboard/preuves/actions.ts` (`ajouterPreuve`, `supprimerPreuve` : accès client propriétaire OU juriste ; storageWrite, événement `PREUVE`) ; composant `src/components/preuves.tsx` ; intégré au détail client `cases/[id]` **et** juriste `juriste/[id]` ; inclus dans l'export RGPD et supprimé (fichiers) lors de l'effacement du compte.
- `Dossier` (type `AMENDE`|`SUSPENSION`; statut `BROUILLON→EN_ANALYSE→A_VERIFIER→PRET→ENVOYE→REJETE→ERREUR_TECHNIQUE→RESOLU→ANNULE`), `pvUrl`, `pvTexte` (texte brut OCR, pour la détection par scan), `extractedData` (JSON OCR), `lettreGeneree`, `motifRejet` (raison du rejet juriste), `decisionOmp` (`ACCEPTE`|`REJETE`) + `decisionDetail` (décision OMP post-envoi), `valideLe` (validation de la lettre par le juriste → kit LRAR), `dateLimite` (délai de contestation calculé par le moteur), `prix`, `failleJuridiqueId` (faille principale retenue), `faillesRetenues` (`DossierFaille[]`). Timeline de transparence : chaque transition écrit un `DossierEvent` (`type` enum CREATION/ANALYSE/LETTRE_GENEREE/EN_ATTENTE/SIGNATURE/VALIDATION/ENVOI/DECISION/REJET/RETOUR/**PREUVE**, `detail` = accusé, motif ou décision) dans le même `$transaction` que le changement de statut ; affichée sur les détails client **et** juriste via `src/components/dossier-timeline.tsx`.
- Moteur juridique : `src/lib/moteur.ts` (pur, sans `server-only`) — `remplirTemplate` (variables `{nom}`, `{plaque}`, `{num_pv}`…), `detecterFailles(data, texte, failles, contexte)` : **base juridique auto-alimentée** — une faille est candidate si **l'une au moins** de ses règles (`FailleJuridique.reglesDetection`, types `champAbsent`/`datePrescrite`/`plaqueIncorrecte`/`etalonnageExpire`/`texteContient`/`texteAbsent`) matche sur les données extraites **et/ou le texte brut scanné** (`Dossier.pvTexte`) ; sans règles explicites, prédicats hérités pour les 4 failles connues ; retour dans l'ordre de priorité (prescription > erreur plaque > mentions > étalonnage), `detecterFaille` = premier candidat (retourne `null` sans indice — plus de « fallback étalonnage » fabriqué). `datePrescrite`, `dateLimitePv` (45 j amende / 2 mois suspension), `joursRestants`, `etalonnageExpire(dateExpiration, datePv)`, `scoreFaille` (score de confiance démo : règles matchées / règles totales, `null` si non candidate ; sans règles, prédicat hérité 1/1). Tests unitaires Vitest dans `src/lib/moteur.test.ts`. `analyserDossier` (`cases/actions.ts`) remplit `extractedData` (saisie humaine, human-in-the-loop), calcule le contexte étalonnage (radar → date d'expiration), enregistre **toutes les failles candidates** dans `DossierFaille` (statut CANDIDATE, après réinitialisation), retient la première comme `failleJuridiqueId`, génère `lettreGeneree` depuis `templateLettre`, calcule `dateLimite` et passe le statut en `A_VERIFIER`. **Questionnaire ciblé (flux A) :** `extractedData` contient aussi `paiementDejaFait`, `vehiculeCede`, `vehiculeVole`, `conducteurDifferent` (checkboxes du formulaire d'analyse, pré-remplis par OCR jamais) — contexte transmis au juriste (affiché sur son détail, aucun article inventé) ; les lettres restent limitées aux `FailleJuridique` validées admin. Si `radarId` est saisi et qu'un `RadarCalibration` existe avec un certificat expiré le jour de l'infraction (`etalonnageExpire`), la faille « certificat d'étalonnage » est retenue et `preuveEtalonnage` (URL du certificat) est stockée dans `extractedData` et affichée sur le détail.
- OCR (Phase 1, garde-fou human-in-the-loop) : `src/lib/ocr.ts` — providers via `OCR_PROVIDER` (`mock` = dev/E2E, `google-vision` = Google Vision API si `GOOGLE_VISION_KEY` set, `mistral-ocr` = Mistral AI hébergement UE/RGPD si `MISTRAL_API_KEY` set, `tesseract` = Tesseract.js local/gratuit, sinon `aucun`), `normaliserPv(texte)` (pur, regex : plaque SIV/FNI, date, heure, montant, n° PV — tests Vitest dans `src/lib/ocr.test.ts`). `createDossier` lance `extrairePv` sur le PV et **pré-remplit** `extractedData` (statut reste `EN_ANALYSE`) ; le formulaire d'analyse (`analyse-form.tsx`, `defaultValue` depuis `prefill`) affiche « pré-remplis par lecture automatique (OCR) » et l'humain vérifie avant soumission. L'OCR n'écrit jamais l'analyse finale seul.
- `FailleJuridique` = base des failles juridiques (typeInfraction, titreFaille, `articleLoi`, `regle` — règle dégagée : ce que l'article + la jurisprudence imposent, `templateLettre` avec variables `{nom}`, `{plaque}`, `{num_pv}`, `{date}`, `{montant}`, `{radarId}`, `source`, `reglesDetection` JSON, `jurisprudence` JSONB (tableau `JurisprudenceRef` avec `resume` — l'essentiel de chaque décision, contextualisé), statut `ACTIVE`/`INACTIVE`/`PROPOSEE`) ; `DossierFaille` (dossierId+failleId unique, statut `CANDIDATE`|`CONFIRMEE`|`REJETEE`) relie chaque dossier à toutes ses failles détectées — les validations du juriste alimentent la base. **Flux SUSPENSION (infra, sans contenu juridique inventé)** : `src/lib/envoi.ts` (pur, testé) fournit les libellés type-aware (destinataire LRAR préfet vs OMP, délais 2 mois vs 45 j, labels du formulaire) ; le formulaire d'analyse (`analyse-form.tsx`) adapte ses labels et masque le questionnaire amende pour SUSPENSION ; callout d'urgence générique « délais de recours très courts » sur les détails client **et** juriste ; l'admin (`admin/failles`) affiche un rappel tant qu'aucun template SUSPENSION `ACTIVE` n'existe. Le catalogue (`catalogue-sources.ts`) porte désormais **3 propositions SUSPENSION** (`verifiee: false` — CE 20 avr. 2021 n° 438114 contradictoire préalable ; CE 14 févr. 2018 n° 407914 marge d'erreur éthylomètre 8 % ; non-notification L. 224-16/R. 224-4 CR) qui arrivent en `PROPOSEE` par l'auto-alimentation — le moteur ne les utilise qu'après validation admin (`ACTIVE`), garde-fou anti-hallucination.
- `Courrier` (`pdfUrl`, `signatureUrl`, `preuveDepotUrl`) lié à `Dossier`
- Dashboard juriste (sect. 9) : `src/app/(app)/dashboard/juriste/` — `requireJuriste()` (JURISTE ou ADMIN) ; file d'attente filtrable par statut (`?f=PRET|A_VERIFIER|ENVOYE|ALL`, union de littéraux typée, pas d'import d'enum) ; détail avec PV, données extraites, faille, lettre + PDF signé ; `juriste/actions.ts` : `modifierLettre` (A_VERIFIER|PRET : met à jour `lettreGeneree`, régénère le PDF avec la **signature existante recollée automatiquement** via `storageRead` + `generateLettrePdf` — composant `lettre-edition.tsx`), `validerDossier` (PRET→PRET : marque `valideLe` + événement VALIDATION, **plus de soumission automatique** — le client envoie lui-même en LRAR), `retournerDossier` (PRET→EN_ANALYSE), `rejeterDossier` (PRET|A_VERIFIER→REJETE, `motifRejet` requis ≥10 car., affiché au client, **crédit rendu au client** dans la même transaction — il peut retenter sans repayer), `enregistrerDecisionOmp` (ENVOYE→RESOLU, `decisionOmp` ACCEPTE|REJETE + note optionnelle ; **pas de remboursement** ici, la lettre a été transmise), `traiterDemandeAvocat` (LawyerMatch DEMANDE→AFFECTE avec nom/barreau/email du partenaire, ou REFUSE avec note ≥10 car.), et `confirmerFaille`/`rejeterFaille` (une faille candidate `DossierFaille` : CONFIRMEE = seule principale + lettre régénérée depuis son template + événement LETTRE_GENEREE « Faille retenue par le juriste » ; REJETEE = écartée + événement ANALYSE) — actions via `juriste-actions.tsx` (useActionState ; `mode="rejet"` pour A_VERIFIER, `DecisionOmpForm` sur les ENVOYE), `avocat-traitement.tsx` et `failles-candidates.tsx` (badges Candidat/Confirmée/Écartée + « Faille retenue » + boutons Confirmer/Écarter). Détail : bloc « Dossier résolu » quand `RESOLU`, et bandeau client RESOLU (acceptée → « amende annulée ») sur `cases/[id]`. Lien « Espace juriste » dans la nav seulement si `role` JURISTE/ADMIN.
- Envoi LRAR (Option A v1) : le client poste lui-même la lettre en recommandé avec AR. `envoyerDossier` (`cases/actions.ts`, client) : PRET validé → ENVOYE + événement ENVOI (détail « Envoyé par le client en recommandé avec accusé de réception »). UI : `lr-kit.tsx` (kit d'envoi : instructions, délai `dateLimite`, PDF, bouton « J'ai envoyé ma lettre ») sur `cases/[id]` quand `valideLe`. La soumission automatisée (RPA/Playwright vers le portail ANTAI réel) viendra en v1.1 : `src/lib/antai.ts::soumettreDossier` (vers `/api/antai/mock`, token `ANTAI_MOCK_TOKEN`, accusé via `src/lib/preuve-pdf.tsx`) reste le point d'entrée mais n'est **plus appelé** dans le flux principal. Page de test manuel `/mock-antai` (dev/E2E uniquement — jamais le portail réel, garde-fou).
- Admin (base juridique) : `src/app/(app)/dashboard/admin/failles/` — `requireAdmin()` ; **vue d'ensemble limitée à l'auto-alimentation** (pas de formulaire « créer » ni d'import/export en UI : la base s'alimente automatiquement, l'admin ne fait que **lire** et **valider/écarter** — actions `modifierFaille`, `basculerFaille`, `importerFaillesDepuisSources`, `validerPropositionFaille` restent disponibles ; `creerFaille`/`importerFailles`/export JSON existent côté serveur mais ne sont plus exposés en UI) et `failles-admin.tsx` (useActionState par ligne). **Base auto-alimentée (recherche documentaire, FAILLES.md §H)** : chaque faille porte une **`regle`** (règle dégagée, affichée sur la carte) et des `reglesDetection` (JSON, éditées dans le formulaire — une règle suffit à déclencher la détection) ; le catalogue sourcé (`src/lib/catalogue-sources.ts::CATALOGUE_SOURCES`, 7 propositions AMENDE + 3 SUSPENSION, chaque jurisprudence avec `resume` contextualisé) s'importe via `importerFaillesDepuisSources` en statut **PROPOSEE** (jamais utilisé par le moteur) puis l'admin les valide (`ACTIVE`) ou les écarte (`INACTIVE`) — `validerPropositionFaille` ; le bouton **« Lire en détail »** expose article, règle dégagée, template, règles de détection et chaque jurisprudence avec son résumé + lien source avant validation. **Formulaire de rédaction guidée** : `FailleFields` (édition seule) propose les chips de variables (`{nom}`, `{plaque}`, `{num_pv}`, `{date}`, `{montant}`, `{radarId}`), un aperçu live du template, un champ « Règle dégagée » et un textarea JSON pour la jurisprudence (avec `resume`). Lien « Base juridique » dans la nav si `ADMIN`. Les templates validés ici sont la seule source des lettres (garde-fou). **Auto-alimentation automatique** : `src/lib/auto-alimentation.ts::synchroniserCatalogue` (idempotente ; upsert complet en PROPOSEE, **enrichissement non destructif** pour les ACTIVE — ne comble que `regle` si vide, ne touche jamais une INACTIVE, ne rétrograde aucun statut) est appelée à l'ouverture de la page admin **et** via `/api/cron/auto-alimentation` (GET/POST, `CRON_SECRET`). **Bibliothèque juridique juriste** : `/dashboard/juriste/failles` (lecture seule, filtres par statut/type, article + règle dégagée + jurisprudence avec résumé + sources affichées) — lien « Bibliothèque juridique » dans la nav.
- Admin radars : `src/app/(app)/dashboard/admin/radars/` — CRUD `RadarCalibration` (`creerRadar`, `supprimerRadar` dans `admin/actions.ts`, `radars-admin.tsx`) : référence radar, `dateExpiration` du certificat, URL de preuve. `etalonnageExpire` permet de vérifier si le certificat était expiré le jour de l'infraction (motif contestable).
